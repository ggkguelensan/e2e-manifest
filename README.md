# E2E Manifest

Принципы поведенческих Playwright E2E: пользовательский сценарий, настоящее приложение, контролируемая HTTP-граница и проверяемый результат.

Самостоятельная документация принципов, архитектуры и проверки поведенческих E2E.

## Что доказывает тест

Поведенческий E2E описывает наблюдаемое поведение пользователя в браузере. Настоящее приложение выполняет маршрутизацию, SSR и гидратацию; тест управляет внешним серверным состоянием.

| Режим | Незарегистрированный HTTP-запрос | Граница доказательства |
| --- | --- | --- |
| `strict` | Ошибка теста | Поведение UI при контролируемом backend-состоянии |
| `passthrough` smoke | Запрос в явно выбранный upstream | Частичный flow при доступности и данных выбранной среды |

Ошибка контракта зарегистрированного стаба проваливает тест в обоих режимах и никогда не включает fallback на upstream. Synthetic E2E не доказывает корректность реального backend и не заменяет QA E2E против интеграционной среды. Адаптер внешнего SDK не доказывает работу реального провайдера.

## Архитектура

Пользовательский путь:

```text
*.spec.ts → *.journey.ts → UI *.pom.ts → Playwright Page
```

Подготовка окружения:

```text
*.spec.ts → Playwright fixture → *.stubs.ts → MSW HTTP runtime → API DTO
                                      ↑
                                *.fixtures.ts
```

| Слой | Ответственность |
| --- | --- |
| `*.spec.ts` | Роль, существенные предусловия, действия и видимые значения |
| `*.journey.ts` | Последовательность пользовательских намерений и композиция POM |
| `*.pom.ts` | Страница, форма, диалог или семантическая область; локаторы и синхронизация |
| Playwright fixture | Выбор серверного arrangement, сборка окружения и journeys |
| `*.fixtures.ts` | Чистые данные HTTP-запросов и ответов |
| `*.stubs.ts` | HTTP-операции и минимальное изменяемое серверное состояние |
| HTTP runtime | Общий API для SSR/browser, политика upstream, валидация и изоляция |
| `api-contracts/` | Zod Mini-схемы опубликованных HTTP-контрактов |

Не пропускай слои: spec не обращается к DOM или HTTP; journey не регистрирует routes и не знает DTO, fixtures и synthetic IDs; POM не знает о стабах и DTO. Инфраструктурные `runtime/*.spec.ts` проверяют HTTP и lifecycle напрямую: цепочка journey → POM относится к behavioral suites.

## Принципы

1. **Один тест — один законченный пользовательский результат.** Сценарий читается сверху вниз как инструкция человеку: действия и наблюдаемые результаты идут в естественном порядке.
2. **Полный простейший happy path — первым.** Критичные роли получают отдельные полные пути; smoke дополняет их. Ошибки, предупреждения, ограничения и альтернативы входят в secondary suite.
3. **Значимые значения видны в spec.** Вход и ожидание записываются явно, даже с дублированием литералов. Ожидаемые комиссии, суммы, даты и статусы не вычисляются кодом теста.
4. **Journey говорит на языке намерений.** Один шаг понятен человеку; весь flow не прячется в одном вызове и не рассыпается на технические клики.
5. **POM скрывает механику переиспользуемой области UI.** Небольшой интерфейс инкапсулирует локаторы, ожидания и mobile/desktop-различия. Он не привязан к fixture или номеру карточки.
6. **Локаторы опираются на доступность и смысл.** Роли, accessible names, labels и видимый текст предпочтительнее CSS, XPath, DOM-цепочек и test ID. Недостающую семантику исправляют в приложении.
7. **Ожидания описывают наблюдаемое состояние.** Используется auto-waiting, без `waitForTimeout`; скриншот, полный DOM snapshot или URL не заменяют доступное смысловое утверждение.
8. **URL проверяется по нужной части контракта.** Для точного маршрута — `toHaveURL('/path')` с `baseURL`; для части URL — predicate по `URL.pathname`/`URL.searchParams`; regex нужен только для маршрута-шаблона. Проверка остаётся в POM/journey.
9. **Поведение UI и внутренняя механика проверяются на разных уровнях.** Stores, callbacks, интервалы, количество polling-запросов, отмена и terminal state модели проверяются unit-тестами.
10. **Данные и HTTP-поведение разделены.** Fixtures чистые, stubs владеют минимальным серверным состоянием, fixture собирает окружение. Arrangement выражает предметные предусловия без искусственного сужения допустимых значений.
11. **Контракт берётся из Swagger/OpenAPI.** Полная ширина DTO, required/optional/nullable, method, path, query, body и response сверяются с документацией. Схема не подгоняется под fixture или ошибку frontend.
12. **Мутация изменяет последующий ответ.** Следующий GET/SSR/reload отражает принятые IDs и значения; заранее зашитый успех не подтверждает корректность mutation.
13. **Настоящие SSR и браузер используют один API.** HTML и гидратация принадлежат приложению. Документы и application API не подменяются через `page.route` или browser service worker.
14. **Политика сети явная.** `strict` изолирован от реального API; `passthrough` явно зависит от upstream. Покрытие стабами и схемами можно наращивать постепенно, не скрывая ограничения smoke.
15. **Состояние принадлежит одному тесту.** Серверы принадлежат worker, handlers и состояние — сценарию. Browser context закрывается перед завершением API-сценария; следующий сценарий ждёт drain принятых запросов.
16. **Время принадлежит сценарию.** Даты строятся относительно общего scenario clock; будущие часы также проверяются. Polling меняет серверное состояние относительно начала ожидания.
17. **Mobile-first покрывает все настроенные устройства.** Один пользовательский сценарий выполняется во всех Playwright projects; профиль не подменяется чужим user agent.
18. **Визуальное доказательство дополняет assertions.** Нет `toHaveScreenshot`, visual-regression baselines и committed PNG. Кадры — временные `*.tmp.png`; в них нет devtools, debug overlays и чувствительных данных.
19. **Отчёт не проникает в продукт и сценарий.** Capture harness временный; screenshot/reporting-код не добавляется в spec, journey, POM или приложение. Один capture manifest служит всем форматам отчёта.
20. **Ошибка остаётся видимой.** Контрактные нарушения и ошибки приложения/гидратации проваливают сценарий, даже если loader перехватил сетевой сбой; CI сохраняет диагностику и оперативно сообщает о падениях.
21. **Проверяется чувствительность теста.** Mutation audit подтверждает, что неверные IDs, значения и контракты делают тест красным. Простого успешного прогона недостаточно для контрактных стабов.
22. **У E2E собственная область правил.** Playwright использует `*.spec.ts`; правила Vitest и размещения unit-тестов рядом с исходниками не переносятся автоматически. Вспомогательные scripts пишутся на TypeScript: `tsx` для запуска, `zx` для shell-оркестрации; новые `.js`/`.mjs` не добавляются.
