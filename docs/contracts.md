# HTTP-контракты

**Когда читать:** добавление или изменение HTTP-операции, DTO, данных или контрактного стаба.
**Определяет:** источник схем, ширину данных и чувствительность проверки.

## Источник и достоверность

Для каждой операции фиксируй происхождение схемы отдельно от её валидации. Method/path, path params, query, body, response, required/optional/nullable и допустимые значения сверяются с доступными доказательствами.

| Источник | Что подтверждает и чего не гарантирует |
| --- | --- |
| Опубликованный OpenAPI | Документированный wire-контракт; соответствие развёрнутой версии требует проверки |
| Backend validators / generated types | Правила соответствующей ревизии; нужно установить происхождение и связь с deploy |
| Ручные frontend-типы | Предположение потребителя; не runtime-гарантия и не доказательство формата wire payload |
| Реальные ответы | Наблюдённые варианты конкретной среды; не полный набор допустимых значений |
| Synthetic fixture | Выбранное условие теста; не источник истины о backend |

Схема сохраняет всю известную документированную ширину shape; поля не удаляются только потому, что текущему сценарию они не нужны.

В локальном `e2e/tmp/contracts.csv` и связанных [JSON-доказательствах](../skills/adapt-e2e-manifest/references/coverage.md) укажи source/revision, статус проверки (`not-run`, `passed-for-samples`, `mismatch`), проверенные операции/варианты и ограничения. Наличие схемы или её прохождение на собственном fixture не подтверждает контракт.

При расхождении установи, неверны ли схема, документ или реализация. Не ослабляй подтверждённое ограничение ради зелёного теста. При адаптации без изменения runtime приложения продуктовое несоответствие фиксируется как долг или препятствие, а не исправляется скрыто.

## Неподтверждённый контракт

Отсутствие OpenAPI не запрещает создавать инфраструктуру и функциональные сценарии. Для операции с одними типами/наблюдениями схема остаётся **предварительной** с явным contract debt. Её задача — проверить известную границу, не выдумывая остальные ограничения.

- Не выводи enum, literal, длины, диапазоны, число элементов или формат ID из одного fixture/sample. Проверяй полный тип, для которого есть доказательство.
- Различай wire payload и результат frontend-преобразований: `Date` в модели не доказывает JSON-формат даты, а нормализованный объект — обязательность всех полей ответа.
- Не запрещай неизвестные поля без подтверждения закрытого shape; используй допускающий расширение объект, сохраняя неизвестные поля для анализа расхождений.
- Required/optional/nullable и union определяются доказательствами. При неопределённости явно допускай ещё не исключённые варианты и записывай, какие ограничения не проверяются. Известные ограничения сохраняются; `unknown`/`any` для всего payload не выдаются за контрактную проверку.
- Разделяй подтверждённые и предполагаемые части одной схемы. Широкая схема уменьшает ложные отказы, но не доказывает реалистичность synthetic данных или полноту контракта.

Проверяй предварительные схемы против реального backend по [согласованному с пользователем плану](../skills/adapt-e2e-manifest/references/backend-validation.md). До доступа и проверки не ужесточай их произвольно и не объявляй полное контрактное покрытие. Сетевая политика strict и достоверность схем независимы: изолированный functional test может иметь неподтверждённый контракт, что отражается в coverage.

## Схемы и данные

`api-contracts/` группируется по сервисам. Файл представляет endpoint или связанную пару request/response. Передаваемые shapes называются `*BodyDTO`, `*ResponseDTO`, `*QueryDTO`, `*PathParamsDTO`. Общая вложенная структура нескольких endpoint — `*Component` в `dto-components.ts`.

Используй выбранный проектом валидатор схем напрямую, без обёрток, скрывающих его семантику. Выбор библиотеки не следует из выбора synthetic backend. Строгий или допускающий дополнительные поля объект выбирается по доказательствам, а не единым шаблоном для всех операций. Отсутствие, optional и nullable различаются по контракту. Неизвестные поля отклоняются там, где контракт строгий.

Данные находятся в `*.fixtures.ts`, HTTP-поведение — в `*.stubs.ts`. Проверяются выбранные схемы операции в обе стороны; ошибка не должна исчезать из-за обработанного frontend сетевого сбоя. Применение request к состоянию описано в [окружении](environment.md#серверное-состояние), транспорт — в выбранном модуле backend; для MSW см. [регистрацию операций](../stack/msw/http-runtime.md#регистрация-операций).

## Mutation audit

Намеренно нарушь существенное условие и подтверди ожидаемое падение именно из-за него:

| Изменение | Что должно обнаружиться |
| --- | --- |
| Неверный path/query/body ID | Нарушение схемы либо предметного соответствия операции |
| Неверное существенное request-значение | Ошибка операции или неверный наблюдаемый результат |
| Неверное response-значение | Нарушение DTO либо падение смыслового assertion |
| Мутация игнорирует принятые IDs/значения | Последующее чтение или UI не подтверждает результат |
| Неизвестный method/path в strict | Ошибка незарегистрированной операции |
| Ошибка зарегистрированного контракта в passthrough | Провал без обращения к upstream для fallback |

Синтаксически допустимый, но неверный ID не обязательно нарушает DTO: проверяй также связь данных и наблюдаемый результат. Простого успешного прогона или отклонения заведомо невалидного JSON недостаточно.

Выполняй аудит для изменённых контрактных операций и существенных зависимых ожиданий. Восстанови исходное поведение, удали временные mutation specs и проверь положительный сценарий. Зафиксируй область и результат по [правилам проверки](verification.md).
