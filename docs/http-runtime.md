# HTTP runtime

**Когда читать:** изменение серверов, proxy, сетевой политики, изоляции или диагностики.
**Определяет:** исполняемую HTTP-границу и её инфраструктурные гарантии.

## Настоящее приложение и общий API

Каждый worker запускает штатное приложение и отдельный локальный HTTP API с MSW на свободных портах. Браузер обращается через same-origin `/api` proxy; SSR, если он есть в приложении, — через серверный API URL к тому же runtime. Мутации видны обоим клиентам и после reload. HTML, маршрутизация и гидратация принадлежат приложению.

Запуск автономен, ручной dev-сервер не является предусловием. Конфигурация использует штатную конфигурацию приложения, задаёт тестовое окружение и отдельные cache/build-каталоги и outputs в `e2e/tmp/reports/` по [локальной политике](local-workflow.md). Devtools, debug overlays и ненужная телеметрия выключены.

Не подменяй документы и application API через `page.route` или browser service worker. Публичные native/SDK-интеграции обслуживают [отдельные adapters](environment.md#внешние-интеграции). Внешняя сеть по умолчанию закрыта; разрешённые интеграции и upstream задаются явно.

## Регистрация операций

Используй стандартные `http` и `HttpResponse` из MSW. Runtime предоставляет `backend.use(...)`; более поздний handler перекрывает предыдущий. Не создавай собственный routing DSL.

Контрактный resolver оборачивается в `backend.contract({ pathParamsDTO, queryDTO, bodyDTO, responseDTO }, handler)`. Method/path принадлежат MSW, query проверяется отдельно. Runtime валидирует переданные схемы, не импортируя продуктовые endpoint самостоятельно. Ошибки собираются до завершения сценария, даже если приложение обработало ошибочный HTTP-ответ.

## Политика сети

| Правило | `strict` | `passthrough` |
| --- | --- | --- |
| Незарегистрированная операция | Ошибка ответа и провал теста | Передача в выбранный upstream |
| Ошибка зарегистрированного контракта | Провал теста | Провал теста без fallback |
| Зависимость от real API | Нет | Явное предусловие |
| Сброс состояния upstream | Не применяется | Не выполняется |

Fixture явно выбирает политику; отчёт фиксирует её и выбранную среду. Автономные synthetic suites используют `strict`. Частичный passthrough маркируется `@smoke`, его предусловия включают доступность и данные upstream. Неконтрактный MSW response допустим в частичном smoke, но не считается проверкой HTTP-контракта. Автономный сценарий имеет stubs всех используемых операций; достоверность и полнота схем оцениваются отдельно по [контрактным доказательствам](contracts.md). Предварительная схема не получает статус подтверждённой из-за strict-политики или зелёного запуска.

## Lifecycle

Application/API servers принадлежат worker; handlers, mutable state и журнал обменов — одному сценарию.

1. Создай чистый API-сценарий, установи handlers и открой browser context.
2. Выполни сценарий.
3. Закрой browser context, затем закрой API-сценарий для новых обработчиков.
4. Дождись завершения принятых запросов (drain).
5. Проверь накопленные нарушения и приложи диагностику, в том числе при падении теста.
6. Освободи состояние; только после успешного drain разреши следующий сценарий.

Поздний ответ не может изменить состояние следующего теста. Если drain не завершается в установленный предел, runtime считается неисправным и не переиспользуется. После сбоя worker Playwright создаёт новый runtime. Cleanup выполняется также при ошибке старта и штатном прерывании; он удаляет только принадлежащие запуску временные каталоги, сохраняя отчёты.

## Диагностика

`api-exchanges` содержит policy, HTTP method, pathname, status и источник ответа (`mock`, `upstream`, `unhandled`). Cookies, authorization, значения query и тела запросов туда не попадают.

Контрактные нарушения выводятся вместе. Необработанные ошибки приложения и ошибки гидратации проваливают тест; ожидаемые продуктовые ошибки, явно смоделированные сценарием, проверяются через UI. Отмена загрузки при закрытии context не считается ошибкой приложения. Trace и остальные артефакты проверяются на чувствительные данные до передачи.

## Инфраструктурные проверки

`runtime/*.spec.ts` обращаются к HTTP/lifecycle напрямую и используют локальный тестовый upstream. Они проверяют:

- запрет следующего сценария до завершения задержанного запроса;
- общее состояние двух HTTP-клиентов и его сброс;
- сохранение body, query и cookies при proxy совместно с частичным stub;
- отказ неизвестной операции в strict независимо от доступности upstream;
- отсутствие fallback после нарушения зарегистрированного контракта;
- сохранение ошибок и диагностики при teardown и падении сценария.

## Команды и режим запуска

Вспомогательные scripts пишутся на TypeScript: `tsx` для запуска, `zx` для shell-оркестрации. `.js` и `.mjs` в E2E-инфраструктуру не добавляются.

Версии Node/package manager берутся из проекта, зависимости — из lockfile; устанавливаются браузеры всех настроенных profiles. Команды отдельно запускают runtime, автономные suites и upstream smoke, поддерживают выбор spec/project и просмотр HTML-отчёта.

По умолчанию все команды выполняются локально. CI/CD не создаётся, не изменяется и не запускается без запроса пользователя; существующий pipeline сохраняется. Timeouts, workers, retries и предел падений задаёт проект; retries не скрывают flaky-результат в отчёте.

Только при явном запросе CI: автономный job проверяет runtime и behavioral suites во всех выбранных проектах, запрещает `test.only` и сохраняет диагностику при падении. Real-backend smoke и выгрузка артефактов требуют отдельного согласованного объёма. Это не разрешает deployment или смену локальной парадигмы манифеста; границы определены в [локальной политике](local-workflow.md).

Приёмка изменения — по [проверкам затронутых слоёв](verification.md).
