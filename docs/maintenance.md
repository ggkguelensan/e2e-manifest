# Сопровождение манифеста

**Когда читать:** добавление или изменение правил, маршрутизации, skills и проектных ресурсов. **Определяет:** как сохранять один источник истины и progressive disclosure без потери обязательных деталей.

## Выбрать владельца содержания

| Содержание | Место |
| --- | --- |
| Общий принцип или граница доказательства | Кратко в README; подробное правило в одном docs-документе |
| Проектное требование | JSON-патч по [протоколу](project-patches.md) |
| Подробности этого требования | Зарегистрированный MD-ресурс патча |
| Повторяемая процедура агента | Skill, ссылающийся на нормативные документы |
| Обнаруженные факты, coverage, evidence, результаты и открытые вопросы | CSV/JSON в `e2e/tmp/` по [локальной политике](local-workflow.md) |

Сначала найди существующее правило, затем редактируй его источник. Не добавляй исправление вторым абзацем в другой документ. Один проект не меняет базу для остальных проектов; общее улучшение требует отдельной задачи на базовый манифест. Не вводи новый skill, если нужен только раздел существующей процедуры.

## Три уровня раскрытия

1. **Вход:** README даёт назначение, обязательные принципы, ограничения полномочий и таблицу «задача → документ». Project README ведёт к базе и manifest index, не переписывая их.
2. **Правило:** документ выбранного слоя или применимый JSON-патч определяет ответственность, критерии решения, необходимые проверки и конкретные ссылки на детали.
3. **Деталь:** MD-ресурс или skill reference объясняет узкую процедуру, формат, исключение либо пример. Он читается только при указанном условии; обязательные ограничения не прячутся в optional reference.

Каждая ссылка должна объяснять, когда нужна цель. Загружай ветку текущей задачи; при расширении scope догружай соответствующий материал. Уже прочитанное не перечитывай без изменения его версии/содержимого. Избегай цепочек файлов, которые только перенаправляют дальше; обычная задача должна находить правило из README и детали из самого правила.

Индекс JSON хранит metadata маршрутизации; MD не дублирует эти поля. В базовых docs достаточно «Когда читать» и «Определяет», а в проектном MD — названия и содержания, поскольку scope/read_when задаёт JSON. Правило без ссылки из точки входа или применимого патча не считается обнаруживаемым.

## Как писать компактно

- Одна область ответственности на документ; разделяй по условиям чтения, а не ради количества файлов.
- Формулируй наблюдаемые требования: действие, граница и способ проверки. Отделяй обязательное правило от иллюстративной настройки.
- Используй таблицу для выбора и прав слоёв, диаграмму для связей, полный пример для неоднозначного преобразования. Не повторяй их содержание соседним текстом.
- Сохраняй условия, ограничения, ошибки, разрешения и критерии готовности. Сокращай повторы, вводные фразы и общеизвестные объяснения.
- Не задавай универсальные размеры файлов и число строк. Если чтение требует нерелевантных процедур, вынеси их за условную ссылку; короткий самодостаточный документ не дроби.
- Храни только актуальное нормативное состояние: без журнала обсуждений, старых подходов, changelog и совместимых копий. Git хранит историю; результаты ревью находятся в tmp.
- Не копируй правила в skill, шаблон, README и project patch. Skill описывает порядок работы и загружает источник правила.

## Изменение и актуальность

1. Определи затронутую гарантию, владельца текста и задачи агента, которые изменятся.
2. Обнови правило, schema/пример и входящие ссылки в одном изменении. Проверь связанные skills и patches; не оставляй противоречащие формулировки.
3. Для патча обнови revision, hashes и сроки только после реального ревью по [правилам времени](project-patches.md#версия-и-время). Изменение общей MD затрагивает всех её потребителей. Невалидную или просроченную metadata нельзя лечить простым переносом даты.
4. При переносе или удалении документа исправь все входящие ссылки и target anchors. Ненужные ресурсы удаляй только после проверки потребителей; не поддерживай alias-копии ради старого пути.
5. Выполни проверки ниже и сохрани результат локально. Публикация, CI/CD и изменение базовой парадигмы не следуют автоматически из правки документа.

## Проверка сопровождения

- Ссылки, anchors, JSON Schema, примеры и Mermaid синтаксически корректны; negative cases проверяют существенные ограничения схемы, включая фактическое отклонение неверных дат, а не только наличие `format`.
- У каждого правила один владелец, у каждого ресурса — путь обнаружения и понятное условие чтения.
- Версия, хронология, срок ревью, hashes и scope применимых патчей проверены отдельно от JSON Schema.
- Пересекающиеся требования не конфликтуют; дата и порядок файлов не используются как неявный приоритет.
- Входной документ не превратился в справочник всех деталей; optional reference не скрывает обязательное ограничение.
- Пройдены реальные маршруты чтения: новый spec, адаптация без E2E, неподтверждённый контракт, проектный override. Для каждой задачи понятны следующий документ, условия остановки и результат без чтения всего комплекта.

Структурная проверка не доказывает поведение агента. Указывай отдельно, что проверено парсером, что прочитано вручную и какой workflow реально выполнен. Не создавай тесты, которые лишь ищут точные формулировки текста.
