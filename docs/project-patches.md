# Проектные патчи и ресурсы

**Когда читать:** подключение манифеста к проекту или добавление проектных требований. **Определяет:** формат, актуальность, загрузку и разрешение конфликтов локальных правил.

## Размещение

Базовый манифест подключается одной зафиксированной поставкой; его файлы внутри проекта не редактируются.

```text
e2e/
├─ README.md                       # вход и команды проекта
├─ manifest.json                   # версия базы и список патчей
├─ manifest/
│  ├─ patches/*.json               # требования, metadata, маршрутизация
│  └─ resources/**/*.md            # подробные правила и справочные материалы
└─ tmp/                            # CSV/JSON рабочих данных, игнорируются Git
```

`README.md` указывает на `manifest.json` и точку входа базы. Индекс соответствует [JSON Schema](../schemas/project-manifest.schema.json), каждый патч — [схеме патча](../schemas/project-patch.schema.json). Это нормативная конфигурация, не данные покрытия; [локальная политика](local-workflow.md) определяет публикацию.

`manifest.json`: `schema_version: 1`, `base.path` относительно этого файла, точный Git commit `base.revision`, список относительных путей `patches`. База доступна локально, её фактическая ревизия сверяется. Пути патчей и ресурсов также относительны `manifest.json`; scope — корню проекта. После resolve все пути остаются внутри проекта. Scope не содержит абсолютных путей, `..`, URL или обхода через symlink. Плавающий HEAD, удалённая автозагрузка и выполнение кода из JSON запрещены.

## Metadata и требования

| Поле патча | Значение |
| --- | --- |
| `schema_version`, `id`, `status` | `1`, уникальный kebab-case ID, `proposed` или `active` |
| `revision`, `base_revision` | Положительный номер редакции патча и точный commit проверенной базы |
| `updated_at` | Время изменения нормативного содержания или metadata, RFC 3339 с timezone |
| `review` | Для active: проверенная `revision`, `reviewed_at`, `review_due_at` в RFC 3339 с timezone |
| `topic` | `scenarios`, `ui`, `environment`, `contracts`, `runtime`, `verification` или `workflow` |
| `scope` | Непустой список файлов/поддеревьев относительно проекта; `.` — весь проект |
| `target` | Документ базы и существующий heading anchor, например `docs/http-runtime.md#команды-и-режим-запуска` |
| `mode` | `supplement` — добавить требование; `override` — заменить разрешённую проектную настройку |
| `reason`, `requirements`, `verification` | Причина, краткие требования и способ проверки; подробности — в ресурсах без копирования |
| `decision_ref` | Для override: конкретное решение пользователя о замене; не разрешение внешних действий |
| `resources` | Явный список MD-ресурсов; пустой, если краткого JSON достаточно |

Supplement добавляет предметные ограничения и требования к устройствам, контрактам, запуску. Override допустим для согласованного стека, profiles, команд, адресации и других настроек при сохранении границ доказательства. Не копируй заменяемый документ: укажи target и проектное отличие. Секреты, результаты запусков и журнал обсуждений сюда не входят.

Патч не может молча разрешить публикацию/CI/CD/real-backend операции, изменение продуктового runtime при адаптации, выдуманное контрактное или a11y-покрытие, смешивание состояний тестов и обход пользовательских ограничений. Изменение базовых гарантий требует явного решения о развитии манифеста.

## Markdown-ресурсы и progressive disclosure

Каждая запись resources содержит уникальный в патче `id`, `path`, `kind`, краткий `summary` и SHA-256 байтов всего файла в `sha256`.

| Kind | Загрузка и содержание |
| --- | --- |
| `rules` | Обязателен при применении патча. Подробные нормативные требования; `read_when` отсутствует |
| `reference` | Загружается только при выполнении условия `read_when`. Примеры, пояснения, процедура конкретной задачи; не прячет обязательных ограничений |

JSON — источник metadata, условий загрузки и актуальности. MD — источник подробного содержания. Не дублируй даты/версии в frontmatter и не повторяй один текст в requirements и MD. Ресурс наследует topic/scope патча и не расширяет полномочия. Если общей процедуры требует несколько патчей, они могут ссылаться на один MD; revisions/hashes всех затронутых патчей проверяются вместе.

Не считай Markdown самодостаточным patch: незарегистрированный MD не становится правилом. Ссылки на другие нормативные проектные MD должны также присутствовать в resources; обязательная зависимость помечается rules. База читается по её маршрутизации. Не загружай соседние каталоги, все ссылки или примеры автоматически.

## Версия и время

При изменении requirements, scope, target, ресурсов, условий загрузки или другого нормативного поля увеличь revision, обнови updated_at, верни status в proposed и проведи ревью. Изменение только результата ревью не создаёт новую редакцию. reviewed_at означает фактическую проверку, а не чтение файла; due_at не продлевается автоматически.

Для применения active одновременно требуются:

- совпадение фактической базы с base_revision и review.revision с revision;
- `updated_at <= reviewed_at <= текущее время < review_due_at`, после приведения timezone к UTC;
- совпадение hashes ресурсов, наличие target/anchor и применимость scope;
- отсутствие конфликтов с другими применимыми правилами.

Срок следующего ревью выбирается по изменчивости требования: контрактам, зависимостям и средам может требоваться более частая проверка, чем стабильному соглашению. Универсального срока нет, но active не бывает бессрочным. Изменение базы или ресурса требует ревью даже до срока. Просрочка, будущая дата ревью, неверный порядок дат или неизвестное текущее время не дают считать правило актуальным. Не используй mtime вместо этих проверок.

## Применение и конфликты

1. Прочитай базовый README и локальный index; проверь версии схем, доступность базы и перечисленных патчей. Не подхватывай файлы других проектов или неперечисленные патчи.
2. По metadata выбери topic/scope задачи. Proposed и устаревшие применимые патчи не действуют автоматически; не игнорируй их молча — отметь затронутое решение как незавершённое до ревью. Независимая работа продолжается.
3. Проверь JSON с date-time format checker, локальные пути, уникальность ID и resource paths, target/anchor, версии, время и hashes. Прочитай нужный раздел базы, requirements и все rules; reference — по read_when. Неизвестный schema_version не обрабатывается по предположению.
4. Совместимые supplements действуют вместе. Override замещает только указанную настройку. Пересекающиеся противоречия, включая MD, не разрешаются порядком списка, датой или глубиной scope: предъяви конфликт пользователю до зависимой работы.
5. Системные инструкции, текущие инструкции пользователя и применимые project agent rules сохраняют приоритет. Патчи не меняют нативную иерархию инструкций.

Валидатор должен реально проверять RFC 3339: включи поддержку format и проверь отказ на заведомо неверной дате; декларация `format: date-time` сама по себе этого не гарантирует. JSON Schema проверяет форму, но не хронологию, hashes, существование anchor или смысл конфликтов. Эти проверки обязательны отдельно. В `tmp/index.json` фиксируй время проверки, базу, patch revisions, hashes загруженных ресурсов, область и результат проверки актуальности.

## Развитие

Каждое добавление проходит [обязательный SSOT-аудит](maintenance.md#обязательный-ssot-аудит): прежде нового патча или MD найди владельца смысла, устрани дублирование в затронутых потребителях и проверь сохранение условий. Совместимое требование в порученной области можно подготовить и проверить без повторного разрешения; неопределённое остаётся proposed. Active не переносится на другую базу автоматически.

Сопровождение, сжатие текста и progressive disclosure определены в [maintenance.md](maintenance.md); отправка предложения upstream — в [локальной политике](local-workflow.md).
