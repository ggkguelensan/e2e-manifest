# Проектные патчи

**Когда читать:** подключение манифеста к проекту или добавление проектных требований. **Определяет:** обнаружение, формат, применение и развитие локальных правил.

## Размещение

Базовый манифест подключается одной зафиксированной поставкой. Его файлы внутри проекта не редактируются. В E2E-корне находятся:

```text
e2e/
├─ README.md                  # вход и команды проекта
├─ manifest.json              # версия базы и список патчей
├─ manifest/patches/*.json     # нормативные проектные требования
└─ tmp/                       # данные адаптации и покрытия, игнорируются Git
```

`README.md` указывает на `manifest.json` и точку входа базы. Объекты соответствуют [схеме индекса](../schemas/project-manifest.schema.json) и [схеме патча](../schemas/project-patch.schema.json). Это конфигурация правил, не данные покрытия; опубликование регулируется [локальной политикой](local-workflow.md).

`manifest.json` содержит `schema_version: 1`, `base` с `path` относительно этого файла и точным Git commit `revision`, а также `patches` — список относительных путей. Источник `base.path` должен быть доступен локально; перед чтением сверяется фактическая ревизия поставки. После разрешения путей база и патчи должны оставаться внутри целевого проекта; scope не содержит абсолютных путей, `..`, URL или обхода через symlink. Не используй личные абсолютные пути, плавающий HEAD, удалённую автозагрузку или выполнение кода из JSON.

## Содержание патча

| Поле | Значение |
| --- | --- |
| `schema_version`, `id`, `status` | `1`, уникальный kebab-case ID, `proposed` или `active` |
| `base_revision` | Точный commit базы, для которого проверено требование |
| `topic` | `scenarios`, `ui`, `environment`, `contracts`, `runtime`, `verification` или `workflow` |
| `scope` | Непустой список путей от корня проекта; путь означает файл или поддерево, `.` — весь проект |
| `target` | Существующий документ базы и его heading anchor, например `docs/http-runtime.md#команды-и-режим-запуска` |
| `mode` | `supplement` — добавление требования; `override` — явная замена разрешённой проектной настройки |
| `reason`, `requirements`, `verification` | Причина, непустой список конкретных требований и способ проверки каждого изменения |
| `decision_ref` | Для override — ссылка на конкретное решение пользователя о замене; не разрешение внешних действий |

Применяй supplement для новых предметных ограничений, требований к устройствам, источникам контрактов и способу запуска. Override допустим для согласованного стека, profiles, команд, адресации и других проектных настроек, если сохраняются границы доказательства. Не копируй заменяемый документ: укажи target и только проектное отличие. Значения секретов и данные текущих запусков в патч не входят.

Нельзя патчем молча разрешить публикацию/CI/CD/real-backend операции, изменение продуктового runtime при адаптации, выдуманное контрактное или a11y-покрытие, смешивание состояний тестов и обход пользовательских ограничений. Нужное изменение базовых гарантий оформляется как явный вопрос о развитии манифеста, а не самовольный override.

## Применение и конфликты

1. Прочитай базовый README и локальный manifest index; проверь версии схем, доступность/ревизию базы и существование перечисленных файлов. Не сканируй чужие проекты и не подхватывай неперечисленные патчи.
2. Прочитай metadata патчей. Для задачи загрузи requirements только активных патчей соответствующего topic и пересекающегося scope, затем нужные разделы базы. `proposed` не меняет правила.
3. Проверь уникальность ID, локальные пути, target/anchor, совпадение base revisions, непустые требования и разрешённость override. При несовпадении не применяй патч и обозначь затронутую область как требующую решения; независимую работу можно продолжать.
4. Совместимые supplements действуют вместе. Override замещает только указанную проектную настройку. Пересекающиеся противоречащие патчи не разрешаются порядком списка, датой или большей глубиной scope: покажи конфликт пользователю до зависимой работы.
5. Системные инструкции, текущие инструкции пользователя и применимые project agent rules имеют приоритет. Патчи — настройки манифеста, не способ изменить нативную иерархию инструкций.

JSON Schema проверяет структуру, но не смысл требований, существование anchor или конфликт областей. Эти проверки обязательны отдельно. Используемую базу и набор патчей фиксируй в `tmp/index.json` для воспроизводимости результатов.

## Развитие требований

Найденное проектное требование сначала классифицируется: рабочие данные идут в tmp, нормативная настройка — в патч. Для совместимого требования в уже порученной области создай минимальный supplement и проверь его; не спрашивай повторно очевидное разрешение на локальную настройку. Неопределённое или конфликтующее требование остаётся proposed до решения пользователя.

При обновлении базы перепроверь target и смысл каждого патча, затем обнови revision. Не переноси active автоматически на другую базу. Если правило полезно всем проектам, подготовь локальное предложение изменения базы; отправка upstream/создание PR выполняется только по явному поручению. При принятии правила в базу убери его дублирование из проектного патча после проверки поведения.
