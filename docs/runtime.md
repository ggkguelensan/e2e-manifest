# HTTP runtime: настоящее приложение и общий API

## Приложение остаётся настоящим

Каждый worker запускает штатное приложение на свободном порту и локальный HTTP API с MSW. В исходной реализации это TanStack Start через Vite; HTML, публичное окружение, SSR и гидратация принадлежат приложению. E2E-конфигурация импортирует обычную конфигурацию приложения и изолирует только cache.

SSR обращается к локальному API через серверный API URL, браузер — через same-origin `/api` proxy на тот же сервер. Мутация доступна последующему browser-запросу и SSR при reload. Ручной dev-сервер не является предусловием автономного запуска.

Не подменяй HTML приложения или его API через `page.route`/browser service worker. Browser session, scenario clock, внешний SDK, anti-bot challenge, deep link и возврат из внешней проверки остаются отдельными узкими адаптерами. Они не подтверждают работу реального провайдера.

## Стандартные MSW handlers

HTTP-операции регистрируются стандартными `http` и `HttpResponse` из MSW, без собственного routing DSL:

```ts
backend.use(
  http.get('/api/catalog/v1/items', () => HttpResponse.json(itemsFixture)),
);
```

Более поздняя регистрация перекрывает предыдущую. Для контрактной операции resolver оборачивается в `backend.contract({ pathParamsDTO, queryDTO, bodyDTO, responseDTO }, handler)`. Path и method принадлежат MSW, query валидируется отдельно. Схемы пишутся через Zod Mini и добавляются постепенно.

Чистые данные находятся в `*.fixtures.ts`; `*.stubs.ts` применяет request к минимальному серверному состоянию. Fixture собирает окружение и возвращает journey.

## Два режима

| Правило | `strict` | `passthrough` |
| --- | --- | --- |
| Неизвестная операция | Ошибка ответа и провал проверки сценария | Передача в выбранный upstream |
| Ошибка зарегистрированного контракта | Провал теста | Провал теста без fallback |
| Зависимость от real API | Отсутствует | Явное предусловие |
| Сброс данных upstream | Не применяется | Не выполняется |

В исходном harness общая MSW fixture по умолчанию использует `passthrough`; готовая synthetic fixture включает `strict`. Частичные сценарии явно помечаются `@smoke`. Простые MSW responses без полной схемы допустимы на первом этапе smoke, но не считаются доказательством проверки всего контракта.

Smoke переводится в `strict` после добавления необходимых стабов и контрактов; одновременно убирается тег `@smoke`. Политика записывается в отчёт. Выбор upstream задаётся конфигурацией окружения, а доступность и данные среды указываются как предпосылки сценария.

## Изоляция и lifecycle

- Application/API servers принадлежат worker; handlers, mutable state и HTTP exchanges — отдельному тесту.
- Browser context закрывается до завершения API-сценария.
- При завершении сценария runtime закрывает его для новых обработчиков и дожидается принятых запросов (drain).
- Следующий сценарий нельзя начать до завершения drain: поздний ответ предыдущего теста не должен изменить новое состояние.
- После сбоя worker Playwright создаёт новый runtime.
- Teardown проверяет накопленные нарушения и прикладывает диагностику, в том числе при падении теста.
- Сброс synthetic state не сбрасывает реальный upstream в `passthrough`.

## Диагностика

Журнал `api-exchanges` содержит политику, HTTP method, pathname, status и источник ответа: `mock`, `upstream` или `unhandled`. В него не попадают cookies, authorization, значения query и тела запросов.

Нарушения контрактов собираются и выводятся вместе после сценария. Ошибки приложения и гидратации также проваливают тест, даже если loader перехватил сетевую ошибку. Отмена загрузки при закрытии browser context не считается ошибкой приложения.

## Проверки инфраструктуры

Runtime-тесты работают напрямую с HTTP/lifecycle и локальным тестовым upstream, без зависимости от dev. В исходном runtime проверяются:

1. Запрет начала следующего сценария до завершения задержанного запроса.
2. Сохранение body, query и cookies при proxy, совместно с частичным стабом.
3. Отказ для неизвестной операции в `strict`, даже при недоступном upstream.
4. Отсутствие fallback в upstream при ошибке зарегистрированного контракта.
5. Общее состояние для двух HTTP-клиентов и его сброс между сценариями.

HTTP-запросы и assertions инфраструктурного теста допустимы непосредственно в `runtime/*.spec.ts`; это отдельный уровень, не behavioral spec.

## Запуск и CI

Версии Node и package manager берутся из проекта, зависимости устанавливаются по lockfile. Перед запуском устанавливаются браузеры настроенных Playwright projects. Runtime, автономные suites и smoke имеют отдельные команды; доступны выбор spec/project, UI-режим и HTML-отчёт.

Автономный CI job сначала проверяет runtime, затем behavioral suites во всех проектах. Upstream smoke запускается отдельно и явно зависит от среды. В исходной конфигурации это ручной job; он не заменяет автономную проверку.

Ошибки выводятся сразу в live reporter, HTML-отчёт сохраняется; установленный предел падений останавливает явно сломанный прогон. Исходный CI использует `--max-failures 3 --reporter line,html`, запрещает `test.only`, допускает один retry в CI и сохраняет trace на первом retry, screenshot при падении и отчёты как CI artifacts даже при ошибке. Конкретные лимиты и профили — настройки реализации, а не универсальные числовые требования манифеста.

Диагностический screenshot при падении отличается от кадра для ревью проходящего flow. Ни тот, ни другой не является baseline и не коммитится в test suite. Галерея для MR/PR создаётся отдельно по [правилам визуальных доказательств](visual-evidence.md).
