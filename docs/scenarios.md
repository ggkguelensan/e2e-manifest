# Сценарии

**Когда читать:** создание, изменение или смысловое ревью behavioral spec.
**Определяет:** язык шагов, Gherkin-перевод и организацию suite.

## Содержание spec

Один `test` ведёт к одному законченному пользовательскому результату. Роль, существенные предусловия, действия, внешние события и наблюдаемые результаты идут в естественном порядке. Промежуточные проверки допустимы, если относятся к этому пути.

Spec получает POM, необязательные Journey и controls через Playwright fixture. Каждый публичный вызов должен иметь понятный смысл без раскрытия реализации. Значимые вводимые и ожидаемые суммы, статусы, даты и выбранные объекты записываются явно; дублирование литералов допустимо. Ожидаемые значения не вычисляются по алгоритму приложения. Постоянные продуктовые формулировки принадлежат POM; текст передаётся из spec, когда он является переменным условием проверки.

Spec не содержит `page`, locators, CSS/XPath, API URL/payload, route interception, synthetic IDs, изменения stores, внутренних callbacks, `waitForTimeout`, подсчёта polling-запросов и ветвления по реализации UI. Вход по подготовленной пользовательской ссылке допустим, когда это условие сценария; переход непосредственно во внутренний этап не заменяет проверяемый путь через UI.

## Gherkin ↔ spec

Из spec можно написать Gherkin без чтения Journey, POM и controls. Из Gherkin должно быть понятно, какие публичные шаги составляют spec. Перевод сохраняет участников, существенные условия, значения, порядок, действия, внешние события и результаты; он не требует догадок или добавления отсутствующих проверок.

| Gherkin | Публичный шаг spec |
| --- | --- |
| `Given` | Подготовка предметного состояния или явно выраженное исходное состояние |
| `When` | Действие через POM/Journey или внешнее событие через control |
| `Then` | Явная проверка наблюдаемого результата через POM/control |
| `And` / `But` | Продолжение соответствующего типа шагов |

Соответствие смысловое, не построчное: один arrangement может задавать несколько связанных условий. Локаторы и технические ожидания не требуют Gherkin-шагов. Один вызов не скрывает самостоятельные существенные действия и результаты. `.feature`-файлы, Cucumber и хранение двух копий сценария не обязательны.

### Полный пример

Пример интерфейсов для приложения с обычной браузерной сессией. Fixture предоставляет перечисленные POM и backend control; `prepare` задаёт серверные данные и сессию, но не открывает страницы и не публикует билет.

```gherkin
Feature: Публикация билета
  Scenario: Продавец публикует билет и видит его в активных продажах
    Given продавец авторизован
    And у него один доступный для продажи билет на «Концерт»
    And комиссия составляет 10%
    When продавец открывает главную страницу
    And открывает «Мои билеты»
    And открывает заказ «Концерт»
    And начинает продажу
    Then он видит один доступный билет, выбранный для продажи
    When он переходит к цене
    And указывает цену 12000
    Then он видит комиссию 10%, сумму комиссии 1200 и выплату 10800
    When он публикует билет
    Then он видит подтверждение публикации
    When он переходит в «Мои продажи»
    Then он видит активную продажу «Концерт» с ценой «12 000 ₸»
```

```ts
import { test } from './seller.fixture';

test('продавец публикует билет и видит его в активных продажах', async ({
  sellerOrders, home, myTickets, orderDetails, ticketSelection,
  salePrice, saleSummary, publication, publicationResult, mySales,
}) => {
  await sellerOrders.prepare({
    authorized: true,
    eventName: 'Концерт',
    availableTicketCount: 1,
    commissionPercent: 10,
  });

  await home.open();
  await home.openMyTickets();
  await myTickets.openOrder('Концерт');
  await orderDetails.startSale();
  await ticketSelection.expectSingleAvailableTicketSelected();
  await ticketSelection.continueToPricing();
  await salePrice.enterAmount(12_000);
  await saleSummary.expectPayout({
    commissionPercent: 10,
    commissionAmount: 1_200,
    payoutAmount: 10_800,
  });
  await publication.publish();
  await publicationResult.expectPublished();
  await publicationResult.openMySales();
  await mySales.expectActiveSale({
    eventName: 'Концерт',
    price: '12 000 ₸',
  });
});
```

## Композиция и suites

Playwright использует `*.spec.ts` и собственные fixtures; правила Vitest и размещения unit-тестов не переносятся на behavioral suites.

Journey сокращает повторяемый путь, когда сам путь не является предметом проверки. Существенные действия и результаты раскрываются в spec. Выбор границ — в [UI-абстракциях](ui-abstractions.md).

Длина spec и число зависимостей не являются самостоятельными метриками качества. Повторяемая связная последовательность может стать Journey; длинный список зависимостей требует проверить связность результата и границы POM, а не создавать общий фасад автоматически.

Основной `*.main.spec.ts` начинается с полного простейшего happy path. Критичные роли получают отдельные полные пути. Ошибки, предупреждения, ограничения и альтернативы размещаются в `*.secondary.spec.ts`. Smoke дополняет полные пути. Название теста описывает наблюдаемое поведение в настоящем времени.

## Проверка перевода

Сформулируй Given/When/Then по spec, сверяясь только с его публичными шагами. Сопоставь с задачей, затем восстанови последовательность spec по Gherkin. Если пришлось додумать условие, раскрыть helper или добавить assertion, исправь интерфейс или сам сценарий. Runtime и чувствительность проверяются отдельно по [правилам проверки](verification.md).
