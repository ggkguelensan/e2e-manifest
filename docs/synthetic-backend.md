# Synthetic backend

## Назначение

Synthetic E2E проверяет поведение браузерного UI при контролируемом серверном состоянии. Политика strict не обращается к реальному API. Частичный passthrough smoke может стабить только нужные операции, а остальные направлять в dev. Такие smoke зависят от доступности и данных выбранной среды; они не доказывают корректность всего backend.

Custom Playwright fixture выбирает arrangement на языке предусловий пользователя и возвращает journey. Spec не собирает backend вручную.

## Разделение данных и поведения

- `*.fixtures.ts` содержит чистые объекты запросов и ответов без `page`, routes и изменяемого состояния.
- `*.stubs.ts` регистрирует HTTP-операции, применяет request к минимальному серверному состоянию и формирует последующие ответы.
- `runtime/mock-api.ts` запускает общий HTTP API для SSR и браузера. Стабы регистрируются стандартным `backend.use(http.get(path, resolver))` из MSW; `backend.contract` добавляет валидацию Zod Mini без собственного routing DSL.
- Browser session, внешние SDK/callbacks и scenario clock являются отдельными инфраструктурными адаптерами. HTML приложения и гидратацию обслуживает TanStack Start. Подмена документов приложения запрещена.

Параметры arrangement отражают ширину предметного состояния, а не только значения текущих тестов. Не сужай `number` до `1 | 2`, если HTTP-контракт допускает произвольное количество.

## HTTP-операция

Для контрактной операции проверяются выбранные схемы:

- HTTP method;
- path params;
- query;
- body;
- response;
- отсутствие неизвестных полей там, где контракт строгий.

Нарушения накапливаются и выдаются после сценария вместе. В strict неизвестный запрос проваливает проверку; в passthrough уходит в upstream. Контрактная ошибка зарегистрированного стаба всегда проваливает тест и никогда не переключается на upstream. Схемы и сценарии можно добавлять постепенно; простые MSW responses допустимы для первого smoke.

Mutation не считается проверенной, если следующий успешный объект был заранее зашит независимо от request. Последующий response должен отражать принятые IDs, значения и изменение серверного состояния.

## Время и polling

Все даты строятся относительно единого scenario clock. Не закрепляй календарную дату, которая со временем окажется в прошлом.

Для polling synthetic server сначала возвращает исходное состояние, а затем меняет его относительно момента начала ожидания. Behavioral E2E проверяет только состояния, видимые пользователю. Интервал, количество запросов, отмена и остановка после terminal state проверяются unit-тестом модели, а не Playwright-сценарием.

Не используй `waitForTimeout`: ожидай пользовательский результат через auto-waiting assertion.

Подробности запуска, lifecycle и диагностики: [HTTP runtime](runtime.md).
