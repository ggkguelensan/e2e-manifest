# Визуальные доказательства

Скриншот дополняет semantic assertion. Он не заменяет её и не становится visual-regression baseline. Screenshot/reporting-код не добавляется в behavioral spec, journey, POM или приложение.

Для выполнения workflow используй [visualize-playwright-flows](../skills/visualize-playwright-flows/SKILL.md): скилл содержит инструкции capture, схему manifest и генератор standalone HTML.

## Выбор результата

До запуска визуализации определи требуемый результат: галерея в конкретном MR/PR или локальный standalone HTML. Если запрос явно называет формат, повторный вопрос не нужен. Если формат не указан, уточни его до запуска capture. Для двух форматов flow снимается один раз, а оба отчёта строятся из общего evidence manifest.

Ссылка на MR/PR сама по себе не разрешает менять его описание. Изменение описания требует поручения на обновление конкретного MR/PR. Генерируемые файлы и capture harness остаются временными, если пользователь явно не запросил repository artifacts.

## Подготовка и capture

Сначала запусти целевой behavioral scenario и подтверди его успешность. Шаги выводятся из spec и journey, а не придумываются по реализации приложения. Временный capture harness нужен только тогда, когда существующего Playwright output недостаточно; он использует публичные интерфейсы journeys/POM.

Для каждой существенной пользовательской проверки:

1. Выполни действие пользователя.
2. Дождись успешной semantic assertion.
3. Дождись сигнала визуальной готовности приложения: загрузки шрифтов и нужных изображений, завершения значимой анимации.
4. Убедись, что devtools, debug overlays и служебные панели отсутствуют.
5. Отметь точную область, подтверждающую ожидание.
6. Сделай отдельный PNG для этой проверки.
7. Удали временный маркер перед следующим шагом.

Ожидания основаны на наблюдении, без произвольных sleeps. Annotation размещается вне содержимого либо добавляется после capture; она не перекрывает UI и не меняет layout. Предпочтителен маркер, привязанный к элементу без изменения геометрии; координатный overlay — запасной вариант.

Один кадр отвечает на один вопрос, а подпись формулирует наблюдаемое ожидание. Accessibility-only состояние подтверждается семантической проверкой; изображение должно доказывать видимый факт. Каждый кадр проверяется вручную на применённые стили, читаемость и правильное положение маркера.

Используй только synthetic identities и данные. Не раскрывай токены, cookies, реальные персональные данные и приватные значения окружения.

## Временные файлы и evidence manifest

Локальные кадры называются `*.tmp.png`. PNG не коммитятся, не используются как assertions и удаляются после загрузки в MR/PR или завершения проверки. Отчёты и manifest хранятся отдельно от test suite; для автономного отчёта assets сохраняются рядом с HTML до завершения его использования.

Manifest лежит рядом с кадрами, пути к изображениям относительны ему. Он содержит:

- `name` в lowercase kebab-case, `title`, при необходимости `description`, `source` и `generatedAt`;
- непустой список `scenarios`, у каждого уникальный `id` в lowercase kebab-case и `title`;
- устройства с `name`, при необходимости `viewport`;
- шаги с `number`, `action`, `expectation`, `screenshot` и описательным `alt`.

Номера шагов — положительные целые, начинаются с одного и идут последовательно внутри устройства. Scenario IDs и имена файлов стабильны. Например, `01-start.tmp.png`.

Каждый кадр проверяется на расширение PNG, PNG signature и ненулевые размеры. Все форматы отчёта используют один manifest и одну съёмку, без повторного прогона на каждый renderer.

## Галерея MR/PR

Перед правкой прочитай актуальное описание. Замени или создай только явно выделенную секцию Playwright flow, сохранив остальные разделы. Публикация галереи не меняет state, reviewers, labels или target branch.

Изображения загружаются через авторизованный upload целевого проекта. Не используй локальные пути, base64 или временный внешний хостинг. Для каждой ссылки проверь принадлежность проекту, успешное скачивание и PNG signature. Если хотя бы одна загрузка отсутствует или невалидна, описание не обновляется.

Группировка: scenario → device → шаги в пользовательском порядке. У каждого шага есть номер, действие, явное ожидание, одно изображение и `alt`. Mobile-кадры располагаются вертикально с читаемой шириной, без узких ячеек таблиц. Длинные flows можно сворачивать; основной сценарий остаётся открытым.

После публикации прочитай описание повторно, сверь количество и порядок изображений с manifest, повторно проверь ссылки.

## Standalone HTML

Отчёт работает без application server, backend и внешнего CDN. Скриншоты — относительные assets, по умолчанию без base64. Он не коммитится без явного запроса на repository artifacts.

Именование: `<playwright-visualization-name>.<file-hash>.html`. Имя берётся из `manifest.name`, hash — первые 12 символов SHA-256 конечного HTML; имена assets содержат hashes изображений, поэтому изменение кадра меняет hash отчёта. Принудительная перезапись допустима после проверки точного пути заменяемого отчёта.

Открой результат в реальном браузере на desktop и узкой mobile-ширине. Проверь порядок навигации, полноту шагов, загрузку и читаемость кадров, keyboard focus, заголовки, отсутствие сетевых зависимостей и чувствительных данных. При передаче результата укажи абсолютный путь HTML и статус артефакта: временный или явно запрошенный для репозитория.
