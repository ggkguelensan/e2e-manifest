# Adapt E2E Manifest

Встрой манифест в выбранный проект и создай недостающую E2E-инфраструктуру. Результат — работающий согласованный набор, локальные правила и таблица покрытия с явными ограничениями. Существующие E2E переиспользуются после проверки; пустой проект получает минимальный полный путь от запуска до отчёта.

## Граница работы

**Не меняй runtime приложения:** компоненты, ARIA/roles/labels/test IDs, бизнес-логику, маршруты, API-клиенты, SSR, production-конфигурацию и поведение сборки продукта. Разрешены E2E-runtime, test-only конфигурация, зависимости и lockfile, локальные команды, POM, stubs и локальная документация. Test-only настройки не меняют штатные значения запуска; не отключай продуктовые проверки ради теста.

Если без продуктового изменения подключение невозможно, подготовь независимые части, укажи точную границу и оставь соответствующую проверку заблокированной. Не обходи её DOM-инъекцией, подменой HTML или изменением stores. Недостающая семантика UI фиксируется как a11y-долг; fallback локатора живёт только в POM.

По умолчанию вся работа локальная. Данные адаптации, покрытия и индексации — CSV/JSON в `e2e/tmp/`, игнорируемом через `e2e/.gitignore`. Без явного поручения не занимайся CI/CD, не делай push/PR/MR и не загружай материалы наружу. [Локальная политика](../../docs/local-workflow.md) — источник границ; [проектные патчи](../../docs/project-patches.md) — способ расширять требования без редактирования базы.

## Вход и маршрутизация

1. Найди целевой репозиторий/worktree, прочитай применимые инструкции, проверь branch/status. Найди корень этой поставки манифеста и прочитай [README](../../README.md) и применимые проектные патчи из `e2e/manifest.json`. Ссылки ниже относительны поставке, команды выполняются в целевом проекте. Skill требует доступ к комплекту манифеста: при отдельной установке выясни его путь или зафиксированную ревизию; не подменяй отсутствующие правила догадками.
2. Прочитай [discovery.md](references/discovery.md). Выполни read-only инвентаризацию и уточни у пользователя стек, границу browser/SSR, источники backend и область первой проверки. Уже полученные ответы сохраняются; вопросы задаются только по неизвестным решениям. Пока ответ нужен для выбора реализации, продолжай независимое обследование, но не устанавливай выбранный за пользователя стек.
3. Зафиксируй рабочие решения в `e2e/tmp/adaptation.json`, навигацию и команды — в локальной точке входа E2E и переходи к [bootstrap.md](references/bootstrap.md): создай или адаптируй инфраструктуру и project rules, затем первый законченный сценарий. При добавлении project rules, патчей или ресурсов выполни [SSOT-аудит](../../docs/maintenance.md#обязательный-ssot-аудит); читай документы по затронутым слоям.
4. Для каждого используемого endpoint установи достоверность схем по [контрактам](../../docs/contracts.md). Если нужна проверка реального backend, прочитай [backend-validation.md](references/backend-validation.md). Она выполняется под присмотром пользователя в согласованном объёме; отсутствие доступа не мешает автономной подготовке, но оставляет контракт непроверенным.
5. Веди [таблицу покрытия и долга](references/coverage.md), включая a11y fallback, источники схем, границы SSR и результаты запусков. Не объявляй полноценное контрактное или accessibility-покрытие по факту прохождения synthetic spec.
6. Выполни приёмку из bootstrap и [verification.md](../../docs/verification.md). Передай команды, проверенную ревизию/профили, границу доказательства, открытый долг и ссылки на локальные правила/покрытие. Укажи отдельно работоспособность инфраструктуры и полноту покрытия; файлы без выполненного запуска не являются готовым внедрением.
