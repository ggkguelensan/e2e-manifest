# Создание и адаптация инфраструктуры

**Когда читать:** после уточнения стека и области. **Результат:** автономный запуск выбранного пользовательского пути с проверяемой тестовой границей.

## Построить минимальный полный набор

Сохрани подходящие существующие реализации; добавь недостающее. Структура файлов следует проекту, ответственности — манифесту.

| Компонент | Действие и критерий |
| --- | --- |
| Runner | Подключить согласованные test dependencies через существующий package manager/lockfile; profiles, reports, запрет `test.only` в CI |
| Запуск приложения | Использовать штатный entrypoint и существующие конфигурационные hooks; test-only overlay, свободные порты, отдельные caches/build/reports и cleanup |
| HTTP runtime | Создать общий MSW API, policy, registration/validation, журнал, per-test state, drain и проверку нарушений по [runtime](../../../docs/http-runtime.md) |
| Test fixtures | Создать lifecycle, browser session, clock и controls по [окружению](../../../docs/environment.md); не скрывать пользовательские шаги |
| Contracts / stubs | Задать provenance и статус валидации; использовать [правила неопределённых контрактов](../../../docs/contracts.md#неподтверждённый-контракт) вместо выдуманного строгого DTO |
| Первый сценарий | Полный выбранный пользовательский результат, Gherkin ↔ spec, нужные POM; Journey только при необходимости |
| Команды | Runtime, behavioral, smoke/real-backend validation отдельно; выбор spec/profile, typecheck/lint E2E, просмотр reports |
| CI | Автономная проверка без real backend; сохранение reports при падении. Согласованный real-backend smoke — отдельный ручной job или иной явно согласованный режим, без автоматического расширения доступа |
| Правила и coverage | Одна локальная точка входа и [реестр](coverage.md), ссылки из применимых project agent instructions |

Test-only изменения общих manifests/config допустимы, если штатные команды и поведение приложения сохраняются. Не добавляй тестовые ветки в components, API-clients, routes или SSR; не обновляй runtime-зависимости продукта ради удобства E2E. Конфликт зависимостей решай test-only изоляцией либо фиксируй препятствие.

Если выбран только browser, ограничение SSR явно отражается в coverage. Если выбран browser + SSR, запускай настоящий SSR и докажи наблюдаемый серверный результат до hydration там, где сценарий от него зависит, затем работу hydration, мутации и reload с общим API-состоянием. Два искусственных HTTP-клиента проверяют runtime, но не заменяют проверку настоящего SSR приложения.

## UI без доступной семантики

Не добавляй ARIA, roles, labels, test IDs или другую разметку в приложение. Найди существующую семантику, текст, атрибуты и область. При необходимости используй [ограниченный fallback в POM](../../../docs/ui-abstractions.md#локаторы-и-assertions) и сразу добавь долг в coverage.

Сценарий должен проверять действие и видимый результат. Если по существующему UI нельзя надёжно отличить нужный объект, не выбирай произвольный `first()`/`nth()` и не подменяй assertion: запиши конкретную заблокированную проверку. Исправление продукта — отдельная задача пользователя.

## Приёмка

1. Запусти инфраструктурные проверки сетевой политики, единого состояния, reset/drain и ошибок. Проверь, что выбранная операция не обслуживается вторым скрытым mock-слоем.
2. Запусти первый законченный scenario во всех согласованных profiles; сверь Gherkin-перевод, assertions и чувствительность. Проверь согласованную browser/SSR-границу на настоящем приложении.
3. Выполни штатные typecheck/lint E2E и приложения, `git diff --check`; проверь повторный чистый запуск и cleanup после ошибки. Не исправляй предсуществующие продуктовые ошибки в рамках адаптации.
4. Сверь diff: продуктовый runtime не изменён, тестовые overrides не влияют на обычный запуск. Не ослаблены продуктовые проверки, DTO или assertions ради прохождения.
5. Запиши в coverage результаты с ревизией и profiles, schema evidence и a11y-долг. Сохрани reports, очисти временные probes. CI считается проверенным только после фактического выполнения job; локальный успех не заменяет его.

Предоставь точные команды и ссылки. Различай «инфраструктура работает», «выбранный путь проверен», «контракт подтверждён в такой-то области», «a11y проверено». При отсутствии необходимых ответов/доступа или при падении сообщи, что создано, что проверено и что конкретно осталось; не выдавай scaffolding за завершённое внедрение.
