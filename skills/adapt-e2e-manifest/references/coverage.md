# Покрытие и технический долг

**Когда читать:** при первом сценарии и каждом обнаруженном ограничении. **Результат:** одна проектная таблица покрытия и связанный индекс долга.

Используй существующий реестр, расширив необходимые поля. Если его нет, создай `e2e/coverage.md` с двумя связанными таблицами: сценарии и долг. Не создавай второй параллельный реестр. Примеры ниже показывают формат, не готовые записи о проекте.

## Сценарии

Одна строка — один самостоятельный сценарий; каждый вариант параметризации учитывается отдельно, повторение на устройствах не создаёт новый scenario ID. ID стабилен при переименовании spec.

| Поле | Содержание |
| --- | --- |
| `scenario_id`, `capability`, `scenario`, `spec` | Постоянный ID, возможность, наблюдаемое поведение и существующий путь; у planned путь пуст |
| `boundary` | Browser либо browser + SSR, сервисы и исключённые части пути |
| `implementation` | `planned`, `implemented`, `blocked`; blocked сопровождается конкретным препятствием |
| `verification_ref` | Ссылка на последний результат: revision, profiles, policy, passed/failed/not-run и report; наличие spec не означает passed |
| `contract_evidence_ref` | Для method/path: источник схемы и revision, validation status, среда/дата/варианты данных, ограничения |
| `debt_ids` | Связанные a11y, contract, topology, SSR или infrastructure gaps |

Подробности операций могут храниться в секции этой же страницы или существующем реестре контрактов; ссылка из coverage должна вести к конкретной записи. Не дублируй results вручную, если report уже является источником истины. Список specs сверяй штатным discovery runner, без запуска real backend.

## Индекс долга

| Поле | Содержание |
| --- | --- |
| `debt_id`, `kind`, `status` | Стабильный ID; `a11y`/`contract`/`topology`/`SSR`/`infrastructure`; `open`/`resolved` |
| `scenario_ids` | Все затронутые сценарии |
| `location` | Страница/компонент и POM/метод либо конкретная HTTP-операция |
| `gap` | Что отсутствует или не подтверждено, без выводов шире доказательств |
| `workaround` | Фактический fallback и его область действия либо причина блокировки |
| `risk_and_evidence` | Риск, способ проверки уникальности/поведения, доступные доказательства |
| `resolution` | Конкретное продуктовое/контрактное изменение и способ подтверждения устранения долга |

Для a11y укажи отсутствующий accessible name/role/label, текущий locator, почему он выбирает нужный элемент, и какой semantic locator станет возможен после отдельного исправления продукта. По возможности укажи owner/issue; не выдумывай владельца и не создавай внешние задачи без поручения.

Пример записи: `A11Y-001`; кнопка закрытия drawer не имеет accessible name; `DrawerPOM.close()` использует существующий `[data-action="close"]` внутри уникальной области, проверяет единственность и закрытие; цель — доступное имя и `getByRole('button', { name: 'Закрыть' })`. Это иллюстрация для UI, где такой атрибут уже существует; добавлять его в приложение нельзя.

Проходящий functional spec с fallback не является a11y-проверкой. Долг закрывается после отдельно разрешённого исправления приложения, замены fallback и успешной semantic-проверки. До этого `implemented` и открытый `a11y`-долг могут сосуществовать. Невозможность надёжно выбрать объект означает `blocked`, а не фиктивное покрытие.
