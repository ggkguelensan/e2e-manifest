# Обследование и решения

**Когда читать:** в начале адаптации. **Результат:** подтверждённая область, стек и карта существующей инфраструктуры.

## Сначала факты

Не устанавливай зависимости и не копируй шаблон до обследования. Проверь:

- приложения/workspaces, manifests, package manager, Node, lockfile, native agent rules и project patches; CI обследуй как задачу только при явном запросе;
- Playwright и другие runners, configs, suites, команды, reports, test-only env и способ запуска приложения;
- где выполняются запросы: browser, SSR/loaders, BFF/server routes, workers; какие адреса и proxy реально используются;
- все источники synthetic backend: MSW handlers, browser service workers, `page.route`, mock servers, framework mocks, fixtures и встроенные dev-моки;
- OpenAPI, generated types, ручные типы, схемы, backend source, доступные среды и происхождение сохранённых примеров;
- существующий реестр покрытия и известные ограничения UI/доступности.

Поиск файлов дополни трассировкой выбранного пользовательского пути и фактического запуска: наличие SSR framework не доказывает серверный запрос, а отсутствие `page.route` в одном каталоге не доказывает отсутствие второго mock-слоя.

## Уточнить у пользователя

Покажи найденные факты и предложи конкретный выбор. Сгруппируй короткие вопросы; не спрашивай снова об уже установленном решении.

| Решение | Что уточнить |
| --- | --- |
| Стек | «Найдено …; сохраняем этот runner, synthetic backend и валидатор схем или выбираем другие?» Установка и замена runners требуют ответа, если стек ещё не выбран. |
| Граница | «Покрываем только browser или также реальные SSR/loaders и гидратацию?» Если SSR обнаружен, объясни, что client-only запуск его не доказывает. |
| Backend | Покажи найденные источники, сервисы, origins и владельцев состояния. Уточни, какие участвуют в целевых suites, какие обслуживают другие задачи и должны остаться отдельно. |
| Контракты | Уточни доступность OpenAPI/backend source и разрешённой тестовой среды. Типы frontend не выдавай за подтверждённый wire-контракт. План реальных запросов согласуется отдельно. |
| Первый результат | Согласуй приложение, законченный пользовательский путь, устройства и объём локальной проверки. Не превращай внедрение в обещание покрыть весь проект. |

Каталог содержит доступные стековые модули, а не обязательный комплект. Если выбран другой стек, запиши решение и соответствие гарантиям; не удаляй существующие инструменты и не объявляй полное соответствие конкретной MSW-архитектуре. Не меняй зависимости до прояснения несовместимого выбора.

## Карта HTTP-границы

Для каждой активной операции выбранного пути запиши `method/path`, настоящий сервис/origin, вызывающий слой, текущий перехватчик, источник данных и владельца mutable state. Несколько реальных сервисов допустимы; несколько независимых ответчиков одной операции внутри одного сценария — конфликт владельцев.

Browser и SSR одной возможности должны видеть один источник состояния. Объедини handlers через общий E2E-runtime или явные adapters сервисов; изолируй конкурирующие перехватчики только в выбранном тестовом запуске. Не удаляй dev/Storybook/unit-моки, которые обслуживают другие задачи, и не оставляй скрытый fallback между независимыми моделями.

Используй существующие env/proxy/config hooks для направления запросов. Если SSR URL жёстко зашит в продукте и без изменения runtime его нельзя направить в test API, зафиксируй препятствие. Не отключай SSR и не подменяй SSR HTML, чтобы назвать browser-тест полным E2E.

## Локальная точка входа

Результаты обследования, карту операций и ответы пользователя сохраняй в CSV/JSON внутри `e2e/tmp/` по [формату данных](coverage.md). До записи добавь `/tmp/` в `e2e/.gitignore` и проверь исключение из Git.

В существующем E2E README или одном новом `e2e/README.md` запиши только проектные решения: ссылку на базу/проектные патчи, воспроизводимые команды, выбранный стек, test env и profiles. Рабочие данные и покрытие только связываются с `tmp/`, не копируются в README. Имена/пути адаптируй к структуре проекта.

Манифест подключается как доступная зафиксированная поставка вне продуктового repository. Постоянная адаптация находится в workdir этой базы; рабочий журнал обследования следует [форматам workspace/adaptation](../../../docs/evidence.md#рабочее-обследование). Project agent rules ссылаются на локальную точку входа, она — на точку входа манифеста и его ревизию. Не копируй правила в несколько файлов, не ссылайся на личный абсолютный путь агента или изменяемый HEAD как на воспроизводимую спецификацию. Не меняй global agent configuration. Нормативные проектные требования добавляй как JSON-патчи и зарегистрированные MD-ресурсы по [протоколу](../../../docs/project-patches.md), проверяя версию, время, scope и конфликты; при развитии правил следуй [руководству сопровождения](../../../docs/maintenance.md); публикация подключения, исходников и материалов не входит в локальную адаптацию.
